# Поддержка браузеров

Нужен WebGL2: актуальные Chrome, Edge и Firefox, а также Safari 15 и новее. Без WebGL2, при
потере контекста, до первого кадра (в это время грузится чанк движка), а также пока экземпляр
ждёт контекст или припаркован, показывается статичный CSS-постер в цветах конфига. Если есть
float-текстуры, свечение считается в HDR, иначе в RGBA8 со сжатием.

Как приложение узнаёт, что постер остаётся, описано в разделе [События](events.md) (событие
`fallback`), а для React в разделе [React](react.md#проп-fallback).

## Что где проверено

- Сквозные тесты в браузере ([Разработка](development.md#сквозные-тесты)) идут в сборках
  Chromium, Firefox и WebKit из Playwright: в CI на Linux-раннере без GPU (программная отрисовка:
  SwiftShader в Chromium, llvmpipe из Mesa в Firefox и WebKit) и локально на Windows с GPU
  (RTX 5090, 165 Гц). Инварианты во всех трёх одни и те же; где браузер медленнее по своей
  природе, у его таймингов свои пределы, и рядом с каждым записан замер, который его объясняет.
- WebKit из Playwright не Safari: на Windows это собственный Windows-порт WebKit, на Linux
  WebKitGTK, у каждого свой GPU-процесс и композитор. На Safari, iOS и Android пока ничего не
  замерялось.

## Чем браузеры отличаются

Замеры на том же десктопе с Windows:

- Firefox компилирует шейдеры каждого нового WebGL-контекста заново (общего кэша программ между
  контекстами нет, `KHR_parallel_shader_compile` тоже): около 1.6 с на контекст, и страница всё
  это время ждёт. Фоны со своим контекстом стартуют и возвращаются после потери контекста по
  очереди в этом темпе (четыре фона: 7-10 с). Общий рендерер компилирует один раз на все свои
  фоны.
- В Firefox `drawImage()` из WebGL-канваса читает весь канвас обратно. Тогда общий рендерер
  копирует через один снимок атласа за кадр, а не через чтение на каждую карточку, и, если так
  дешевле (решает замер), читает снимок через `readPixels`, только используемую часть. Сотня
  карточек на одном экране всё равно тратит там на копии 15-25 мс за кадр (примерно на четверть
  меньше, чем со снимком, нарисованным из WebGL-канваса: 41 против 34 fps), а в Chrome меньше
  1 мс, поэтому снижение стоимости сильнее урезает частоту и разрешение.
- Windows-порт WebKit блокируется на первом прогреве шейдеров нового контекста (`fenceSync` там
  ждёт GPU-процесс), а шейдеры восстановленного после потери контекста компилирует заново. Кроме
  того, первый кадр канваса он показывает позже, чем изменение стиля, которое канвас открывает,
  поэтому новый или восстановленный канвас появляется со вторым кадром (во всех браузерах: на кадр
  позже, чем раньше).
- Firefox пишет предупреждение о каждой потере WebGL-контекста, в том числе о тех, что
  библиотека освобождает сама. WebKit считает освобождённые контексты в свой лимит в 16 штук,
  пока их не соберёт сборщик мусора, и пишет ошибки, когда отправляет один из них в переработку.
- `performance.now()` в Firefox и WebKit идёт шагами по 1 мс (в Chrome по 0.1 мс), а GPU-таймер и
  Long Tasks API из трёх есть только у Chromium: в Firefox и WebKit адаптивное качество, снижение
  стоимости и выбор способа копирования работают по средним за несколько кадров.

Общий рендерер, его копии через снимок и снижение стоимости описаны в разделе
[Много фонов на одной странице](many-instances.md), адаптивное качество в разделе
[Производительность](performance.md#разрешение-и-адаптивное-качество).
